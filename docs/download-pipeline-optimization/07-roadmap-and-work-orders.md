# 分批落地路线与工作包

状态：全部为[RECOMMENDATION]，**没有已实施任务**。本轮交付的是方案；以下工作包是后续可选实施单位，不是已经执行的代码修改或发布承诺。

## 1. 第一批建议与原因

先选四组独立可评审的边界，不等完整框架改造：

1. **执行能正常结束**：E01/E02，修终态先后和after_fix取消。收益与具体失败条件直接对应。
2. **解析能释放且不过期回填**：I02和I03的epoch部分，避免旧UI结果与缓存复活。两种generation分别处理。
3. **材料和日志安全**：C02的try保护区、C04的源头脱敏，C01先返回明确同步结果。暂不升级整个认证存储协议。
4. **提交现场可解释**：先给A03占位异常和A01/A02危险窗口补隔离故障证明，实施小范围所有权修复；新journal协议必须完成兼容审查后再接入。

不把“同时开四组”当作可以并行编辑workers.py。实施可并行调查/写测试，但共享文件须单owner提交，接口冻结后串行整合。

## 4. 每包统一评审模板

```text
目标需求 / 提案ID / 受影响模式
旧行为证据 → 新行为与处理缘由
接口owner / 状态写者 / 新增资源 / 终结与清理
最小复现或故障夹具 / 测试层级 / 已执行结果
旧任务与旧journal兼容 / 回滚前置 / 新数据保留方式
剩余未知 / 是否允许扩大接入范围
```

不得把“代码更短”“测试数量增加”作为单独验收依据。每次必须写出可观察的正确性变化和代价；性能包还要包含相同条件的前后分布与资源量。

## 5. 回滚与交付门槛

纯内存adapter可在无活动run时回退，但已修的安全边界作为小补丁保留。写新Plan或receipt前必须证明旧读者行为；写新journal后不能回退到会扫掉它的旧路径。新旧writer或恢复器不可同时认领同一任务/receipt。

退出屏障失败时不得自动强杀文件提交线程并宣称正常关闭；用户强退属于另一动作，必须准确表达未完成材料。未知现场的删除或跨卷迁移属于有独立对象范围的后续操作，本研究不执行。

完成一包后更新V2事实章节与本目录实施状态；未实施提案继续保持RECOMMENDATION。最终发布还需项目既有构建、冻结环境和release门，文档检查不能代替它们。
