# 日志问题分析与改良方案

日期：2026-09-12。范围：FluentYTDL 当前工作区代码（含已有未提交改动）、本地应用日志、结构化 trace、查看器与诊断包。本文是设计评审，未修改业务实现。

后续状态：用户已授权并完成源码实施，功能落点、验证和边界见 [实施记录](LOGGING-IMPLEMENTATION-2026-09-12.md)。以下内容保留为实施前分析。

## 1. 结论与证据边界

现有系统已有结构化事件、五级关联标识、失败诊断、原始输出留存、线程异常捕获和任务时间线，适合增量修正。主要问题集中在**状态语义不准确、测试混入运行日志、会话证据缺失、导出不完整、脱敏入口不统一**。

本次读取时，`logs/app_2026-09-12.log` 为 343,120 字节，包含 1,022 条带时间头的记录：INFO 780、DEBUG 178、WARNING 53、ERROR 11。多行堆栈不重复计数。其中至少 8 条 ERROR 的调用模块明确为 `test_i18n_runtime`；不能将全部 11 条解释为用户运行故障。测试调用业务模块产生的日志仍显示业务模块名，因此按 `test_` 排除只能得到下界。

`logs/traces/*.jsonl` 当前共 29 个文件、145 条可解析事件，未发现损坏 JSON 行；其中 outcome 5 条。样本可能混有测试，不用于推算生产成功率。日志目录递归共 91 个文件、约 6.73 MiB，应用日志及压缩件 60 个，最早文件名日期为 2026-04-23。当前没有磁盘容量危机，但“只保留 7 天”的配置并没有清理掉全部历史文件；旧文件来源、历史命名和轮转触发条件仍需进一步核对。

## 2. 实际日志中的问题

### 2.1 完成状态提前发布：P0

任务 `1638`，flow `31f5b4`，run `1af9d7`：

| 时间 | 事件 |
|---|---|
| 14:01:12.115 | processing → completed，97% |
| 14:01:12.120 | completed → processing，97%，WARNING |
| 14:01:12.290 | processing → completed，99% |
| 14:01:12.306 | actual matched=true |
| 14:01:12.317 | outcome=success，degraded=false |

证据：`logs/app_2026-09-12.log:184`、`logs/traces/flow-31f5b4.jsonl`。

当前代码 `download/workers.py:1504、1561、1855、1882` 在“核对产物”“整理文件”期间调用 `force_update("completed", ...)`。`download_manager.py:425` 会接受这些状态并排队写数据库；`_emit_transition()` 只报警，不阻止回退。这不是单纯文案问题。日志证实曾发送提前完成状态，但本次没有检查当时的数据库快照，不能据此断言发生了数据丢失。

**设计**：核对和整理期间保持非终态 `processing`，用 stage 区分 `verify/finalize`；只有产物提交成功后发布 completed。保留 transition 的唯一生产点。拒绝同一 run 已封闭后的迟到进度，并记录一次 signal；新的 run 允许重新开始。不要简单屏蔽回退警告来掩盖提前完成。

### 2.2 Cookie 警告重复，但这次任务成功：P1

同一下载在 14:00:40—44 连续出现 5 次 cookies invalid 警告；解析和下载还各有一条结构化 `cookie_expired` signal。最终 expected/actual 匹配，outcome=success。这里应表达“观察到认证异常征兆，当前任务仍完成”，不能将警告自动升级成任务失败。

**设计**：按 session/flow/run/attempt + code + component 聚合重复警告，显示首次、末次和次数；保留诊断原文及不同重试轮次证据。成功路径继续只发 signal，不调用 diagnose。账户级健康状态可提示用户检查登录状态，不能从这些警告直接证明当前认证文件无效，更不应触发循环刷新。

`download/features.py:191` 将 `embedsubtitles=False` 记成 WARNING；正常的用户关闭功能应为 DEBUG 或配置事实，仅“用户要求嵌入而实际缺失”才属于降级。

### 2.3 旧日志中的 unknown 缺少可行动信息：P1

9 月 9 日任务 1635 的 `FileNotFoundError: [WinError 3] ... 'E:\\'` 被归为 `code=unknown`（日志 462—463 行）。另两次解析失败包含多个 cookie_expired 征兆，但主因仍 unknown（323、361 行）。前者可以增加本地异常类型/errno/winerror 分类；后者不能仅凭同时出现 Cookie 警告就强判 Cookie 是根因。

**设计**：本地文件错误记录 `exception_type/errno/winerror/operation` 和脱敏路径；区分路径不存在、权限不足、空间不足，并给出对应操作建议。unknown 保留候选征兆、最终退出码、未命中原文及分类规则版本，形成后续规则改良样本。

9 月 9 日还有一条 CRITICAL 来自 `File "<string>", line 1` 的 POTManager AttributeError，更像脚本探针调用错误；现有证据不足以认定为 GUI 崩溃，也不能宣称当前仍可复现。历史业务问题应逐项回放后确认是否已修复。

## 4. 诊断包与查看器设计

### 4.1 诊断包：P1，优先于界面美化

现状：`bundle.py:96` 总取最新 app 日志；`_meta()` 写当前导出进程的版本和 session；单文件失败直接 continue，最后仍报告候选文件总数。UI `_export_bundle()` 同步调用压缩。历史任务可能附带错误日期的应用日志和当前环境，并且部分导出缺失不透明。

方案：

1. 任务选择提供 task/flow/run/session；恢复任务涉及多个 flow 时收集相关运行，不只取第一个 identity 命中。尚未创建 task 的解析失败也允许按 flow 导出。
2. 读取关联 session 快照及任务运行时间窗，选取对应日期/压缩日志；区分 `source_runtime` 与 `export_runtime`。保留共享 flow 中必要的解析上下文，避免无关任务的大量细节。
3. 导出包含 `manifest.json`：选定范围、实际写入文件、缺失/失败原因、截断标志、脱敏策略版本、源文件大小、包内文件哈希。部分完成显示“部分导出”，不可假报完整。
4. 显式记录应用构建标识、工具版本、有效配置摘要和诊断规则版本。启动快照存入 session 文件，任务引用快照 ID，避免每个事件重复保存全量配置。
5. 后台执行扫描、脱敏和压缩，通过 Qt Signal 返回进度与结果；先写临时 ZIP，完整关闭后原子替换目标。设置单包字节预算，例如初值 30 MiB；超限明确截断规则，优先保留 diagnosis/outcome/identity/关键原文。
6. 导出前设置可确认的写入屏障，等待此前已接收事件写入；导出时记录快照截止点。同步日志不等于断电持久化，不应承诺任何强杀场景均零丢失。

### 4.2 查看器：P1/P2

现有缓冲已有上限（文本 1000 行、事件 3000 条），应保留。问题是读取、压缩和逐条渲染仍在 UI 路径：deque 限制了内存，却仍需扫描完整文件；搜索每次输入重建列表；历史加载完才连接实时信号存在交接空窗。历史文本匹配只保留秒级时间，跨日同秒同消息可能误配。时间线默认只读最近 3 个文件，用户无法完整回查历史任务。

设计：

- 基于记录 `record_id/event_id` 去重；新增字段属于 metadata，保留现有 EventKind 闭集，不修改现有文本 sink format。
- 先建立实时缓冲，再后台加载到指定快照点，最后按 ID 合并，避免丢失/重复；旧格式用兼容读取器，并保留完整日期与毫秒。
- 默认展示当前会话摘要；按任务/run、时间范围、级别、错误码搜索。支持“加载更早记录”，标明当前仅加载部分历史。
- 使用定时批量渲染（建议 50—100ms）和搜索防抖（150—250ms）；队列有上限，丢弃低优先级显示记录时提示数量，不能静默丢失 diagnosis/outcome 的持久记录。
- 任务摘要显示终态、耗时、重试次数、主要诊断、缺失产物；重复警告显示次数并可展开原文。保留中文展示/稳定诊断原文双层设计。

建议的数据流：

```text
业务边界 → 现有 emit_event / log_text → 统一身份与脱敏
                                      ├─ app 文本 + display 元数据
                                      ├─ session 或 flow/task JSONL
                                      ├─ 最小同步错误记录
                                      └─ Qt 批量显示队列
关联 session + flow + run 的快照 → 后台脱敏导出 → 带清单的诊断包
```

| 阶段 | 交付内容 | 必须通过的验收 |

| A：记录可信 | 测试目录隔离；提前 completed 修正；sink 脱敏设置统一；session 路由 | 运行测试前后真实日志哈希不变；97/99% 无 completed；提交后一次最终 success；无 flow 的配置可读回；模拟秘密不出现在各落盘通道。 |
| B：证据完整 | 轮转修复；sink 健康状态；路径统一；按关联运行导出 | 低阈值连续跨 3 次轮转、同秒写入不丢记录；安装失败后可重试；权限拒绝/磁盘满不影响业务但可见；历史任务包附带正确 session 和日期，缺失文件明确列出。 |
| C：定位高效 | 警告聚合；异常类型分类；查看器后台读取、无缝交接、历史分页 | 重复警告计数正确且不跨 attempt 混淆；成功带征兆仍保持 success；路径错误不再笼统 unknown；边写边打开查看器无漏重；跨日同秒日志不误配。 |
| D：长期稳定 | 保留策略与负载验证 | 持续高频写入时验证内存/磁盘边界；历史读取、搜索、导出不阻塞操作；Qt 主线程响应目标 p95 小于 100ms，作为待测目标而非当前性能承诺。 |

业务回归覆盖视频、VR、频道、播放列表、字幕、封面六种流程；覆盖重试、暂停/恢复、取消、后处理失败、提交后异常。保持项目既有契约：transition 单生产点、diagnosis 仅失败边界、degraded 仅 expected−actual、每 run 一个 outcome、观测失败不影响业务。
