# 下载链路优化研究 · 目标与边界

日期：2026-09-19。状态：**分析与设计建议，未实施业务变更**。本目录独立于[新版架构 V2](../architecture-v2/NEW_ARCHITECTURE_REFERENCE.md)：V2回答“实际怎样运行”，本目录回答“为什么如此、哪里值得改、怎样证明更好”。不覆盖或改写V2事实基线。

## 1. 任务解释

用户要求以新版架构书为基础，分析各部分作用、拆分下载链路、寻找各处更优解并另建文件夹。“四处”按各环节理解，不人为限制为四条建议。主范围是URL输入直到文件交付、历史保存、取消、退出和恢复；认证/POT/工具选择是支撑依赖。应用升级、安装器与云端公告只列相邻约束，不扩成另一轮全系统重构。

这里的“更优”按**用户文件与身份正确性 → 能正常结束及恢复 → 结果可解释 → 响应与性能 → 维护成本**评估；不以新增抽象数、减少代码行数或堆并发作为目标。性能收益只能提出可检验假设，本轮不填写虚构基线或提升百分比。

## 2. 用户可见目标与验收要求

下列为[RECOMMENDATION]，是后续实施的验收合同，不描述现有系统已经满足。

| 要求 | 当发生什么时，系统应如何响应 | 重要性与依据 |
| --- | --- | --- |
| G01 意图一致 | 当任务排队后全局设置变化时，已接受的模式/输出意图仍按任务策略执行；旧任务迁移应可解释 | 防止排队时选择与执行结果不同；不能连带永久冻结过期凭据或签名URL |
| G02 可终结 | 当用户在解析、下载、暂停或等待修复时取消，所有对应等待者最终结束并释放内部容量；提交临界区按文件安全规则延后响应 | V2 R11/R12/R18/R28/R29 |
| G03 文件安全 | 当提交或日志写入失败时，不误删未知归属文件；已交付文件不被收尾异常反转为失败；未知恢复现场可被识别与处置 | V2 R01/R25/R26/R27 |
| G04 状态一致 | 当文件已交付但历史写入失败时，区分两种结果并能后续对账；writer停止返回可核对结果 | V2 R13/R14；不声称文件系统与SQLite存在共同事务 |
| G05 身份明确 | 当账户切换或凭据刷新失败时，说明选择账户与有效材料的差异；匿名任务不附带身份 | V2 R07/R08/R10；保留弱回退的旧材料保护价值 |
| G06 支撑隔离 | 当一个任务取消或POT不可用时，不关闭另一个任务/实例仍拥有的资源；错误指出具体前置阶段 | V2 R03与资源所有权 |
| G07 响应可测 | 当批量解析/创建任务或后台写入时，能测量UI延迟、队列等待及资源峰值，再决定优化 | 原来没有性能测量结果，先建对照实验 |
| G08 六模式不退化 | 当共享控制与资源代码调整时，视频、VR、频道、播放列表、字幕、封面及音频/片段变体保持既有有效行为 | 六入口不等于同一执行策略 |
| G09 迁移可退 | 当新计划或journal格式写出后回退程序版本时，不让旧读者删除或错误解释新现场 | 回滚不是简单切换代码；需格式/路径隔离与旧版本实测 |

## 3. 必须保留的约束

- yt-dlp继续通过CLI执行；遵守[仓库规则](../../AGENTS.md)的Cookie匿名快照、无sleep_interval、语言匹配和插件部署约束，不以未经验证的新client策略优化成功率。
- Staging保持所有产物通道的交付owner，Feature不能自行提交最终路径；committed是不可逆成功边界。拟改恢复机制必须正面处理journal写失败，不能靠改注释提升保证。
- transition单一生产者、每run唯一outcome、diagnosis只属失败边界、无逐进度结构化事件洪水；新测量不另造EventKind。
- task/run/attempt/transaction不同身份继续存在；live pause和after_fix不能被随意变成新run。
- 自管工具/凭据和managed资源边界保留；本轮不改变用户自管文件策略。
- [已有元数据设计](../../specs/media-metadata/design.md)是未实现的独立方案。新的任务计划容纳它的策略版本，后处理保留它的candidate→verify→adopt思路，不再平行创造一套元数据owner。
