第二次补充（同日）：隐藏任务窗口最外层正文滚动条，保留滚动和焦点可达；修正窗口缩放、手风琴开合时的背景绘制，并处理深色流表交替行的浅色底纹。最新实现与验证记录见 IMPLEMENTATION.md。

## 1. 范围与证据

- [Issue #105](https://github.com/SakuraForgot/FluentYTDL/issues/105) 仍为 OPEN。正文报告新建任务窗口过长，下载位置和下载按钮不可见，滚动不能到达；评论另有竖屏用户需要改成横屏才能操作。
- 本次检查的本地基线：`main` / `v3.7.5` / `76a16fd2b25c82a4f9fe624fedb8eb131d7ff7c0`。开始时工作树干净。Issue 没有给出准确程序版本、分辨率、缩放或任务栏配置，不能把当前源码测量值当作报告者机器的参数。
- 本地依赖：PySide6 6.10.3、PySide6-Fluent-Widgets 1.10.5、PySideSix-Frameless-Window 0.8.1。
- 实验使用真实 Qt 控件及 `on_parse_success()`，但使用 offscreen 平台、合成视频信息和模拟 `availableGeometry()`；禁用解析、缩略图请求、Cookie 预检及账户列表读取，数据目录隔离。没有进行下载或真实登录。
- offscreen 默认中文字体缺失，初次测量为 817/940 高；加载本机微软雅黑并采用入口程序的字体配置后复测为 846/975。下文采用后一组结果，说明字体也影响布局下限。

- 离屏结果证明布局和控件命中问题；不等于已复现 Windows 真机的原生拖动、混合 DPI、最大化及安装包行为。

## 2. 已确认的原因

### 2.1 内容直接参与顶层最小尺寸，外层没有滚动容器

`download_config_window.py:387–422, 558–563` 中，内容通过 `viewLayout`、`contentLayout` 直接加入顶层布局，底部按钮也在同一顶层纵向布局中。页面内部的预设列表、格式表可以滚动，但下载选项、裁切、下载目录没有共同的滚动视口。

`_get_target_geometry()` 在 1224–1228 行把目标高度截到屏幕可用高度；这只是目标矩形。布局随后重新设置最小尺寸，能够把实际窗口撑得更高。初始化或动画前调用 `setMinimumSize(0, 0)` 不能永久解除子控件布局产生的约束。

因此只修改 `resize()`、初始高度或再加一次高度截断不能解决问题。需要改变布局层级，使内容最小高度由滚动视口承接。

### 2.2 隐藏的专业页面抬高简易页面下限

`platforms/youtube.py:773–850` 将简易和专业页面装进 `QStackedWidget`；专业页面的表格滚动区域最小高度为 288。

本次实测（逻辑像素）：简易子页面最小尺寸为 179×96，专业子页面为 396×356，当前显示简易页面时，堆叠容器仍报告 396×356。这使简易模式也承担专业页面的高度下限。

另外，`_build_single_option_switches()` 使用一行 `QHBoxLayout` 排列字幕、封面、嵌入、元数据等控件，本次测得该行最小宽度为 691；加上左右边距后，整窗最小宽度提示为 739。即便移除显式锁宽，也必须处理内容的横向下限。

### 2.3 裁切动画明确允许内容超过屏幕高度

`_animate_for_section_expand()`（2295–2319 行）读取布局最小高度，加上裁切展开高度，然后传入 `_animate_height_keep_center()`。

后者在 1182 行使用：

```python
target_h = max(1, int(min_h), min(int(target_h), avail.height()))
```

当 `min_h > avail.height()`，结果仍然超过屏幕。现有注释也说明了这一取舍：避免 Qt 再次撑开而优先满足布局高度。这能在大屏保持展开时的居中，却无法保证小屏底部按钮可用。

### 2.4 宽度和横坐标没有完整的屏幕约束

模式目标尺寸（1124–1134 行）：

| 模式 | 目标宽×高 |
| --- | --- |
| 普通单视频 | 760×880 |
| VR | 880×750 |
| 播放列表／频道 | 980×760 |
| 字幕／封面单条 | 760×520 |

`_get_target_geometry()` 只截高度、调整 y，不截宽度、不夹 x。动画结束后，1166–1167 行又把最小宽度设回模式宽度，最大宽度设为模式宽度加 60。即便前面新增宽度截断，结束回调也可能再次撑宽。

以 720 宽逻辑屏幕为例，普通单视频会得到 x=-21、宽 760 的窗口；播放列表 980 宽的风险更高。狭长屏上可能同时存在左右裁切和高度不足。

### 2.5 标题栏左上角存在独立的鼠标命中死区

窗口先创建标题栏并 `raise_()`，随后创建 `main_widget = QWidget(self)`，把布局建在它上面，最后又用 `self.setLayout(self.v_layout)` 将布局移到窗口上。

结果是一个没有布局的 `main_widget` 留在窗口左上角，实际矩形为 `(0, 0, 100, 30)`，层级高于标题栏。当前类没有后续 `showEvent()` 再提升标题栏。

离屏 `childAt()` 实测：

- y=16，x=20、50、99：命中遗留 `main_widget`。
- y=16，x=101、200、400：命中 `ThemedTitleBar`。
- 实验中对标题栏执行 `raise_()` 后，x=20 重新命中标题栏，三个屏幕案例均相同。

本地依赖的拖动入口位于标题栏 `mouseMoveEvent()`，调用 `startSystemMove()`。所以被遮挡区域没有正常的标题栏拖动入口。这证明的是局部死区，不能推断整条标题栏在所有机器上均无法拖动；全区域拖不动仍需真机复现。

### 2.6 专业模式的滚动与卡片展开实现不统一（新增）

用户描述的“下拉栏”先按可见交互分成卡片展开／收起、列表滚动条、下拉选择菜单三类核验，避免修错对象。目前确认的源码事实如下：

| 交互位置 | 当前实现 | 已确认的差异 |
| --- | --- | --- |
| 普通专业模式音频／视频流表格 | `youtube.py:873–898` 的原生 `QTableWidget` | 未配置 Fluent 平滑滚动委托，也未显式设置逐像素滚动 |
| 普通专业模式流卡片的外层 | `youtube.py:846–850` 的 `SmoothScrollArea` | 与卡片内原生表格不是同一套滚动实现，鼠标落点可能改变滚动响应 |
| VR 专业模式音频／视频流表格 | `vr.py:501,539` 的 Fluent `TableWidget` | 普通／VR 表格基础组件不同，应统一检查滚动、选中和视觉效果 |
| 音视频流卡片的展开箭头及正文 | `youtube.py:632–698` 的共享 `FormatExpandCard`，VR 也复用 | `toggle()` 直接换 UP/DOWN 图标并 `show()/hide()` 正文，没有高度过渡或箭头旋转动画 |
| 下载模式、输出容器、音频格式菜单 | `youtube.py` 中的 Fluent `ComboBox` | 源码已共用控件类型；是否存在不同弹出方向、空间裁切或动画观感问题仍待逐项观察 |

普通模式的流表格又在 `_populate_table()`（1198–1204 行）按最多两行设定高度（`fill_content=False` 时），超过两行后需要内部滚动；单表模式则使用 `fill_content=True` 展开全部行并由外层滚动。两条路径的滚动承担者也不同。

音频与视频卡片共用一个展开类，普通模式两张表格也由同一工厂创建；不能据此断言它们分别使用了不同动画。已确认的是组件混用和展开动画缺失；用户所指的具体两处，以及行数、可用高度、鼠标位置是否造成差异，需要有针对性的运行对比。本轮没有录制动画或测量帧耗时，尚不能给出“已复现卡顿”或流畅度提升结论。

## 4. 为什么高分辨率屏幕仍然触发

Qt 的窗口尺寸和屏幕几何使用设备无关像素，物理像素由系统缩放换算。1920×1080 / 150% 约对应 1280×720 的逻辑桌面；再扣任务栏，可用高度会更小。2560×1440 / 200% 也约为 1280×720。因此不能按“1080p／2K／4K”单独判断能否放下窗口。[Qt High DPI](https://doc.qt.io/qtforpython-6/overviews/qtdoc-highdpi.html)

上面的换算仅作解释，不是已测硬件组合。实现应直接使用目标 `QScreen.availableGeometry()`；不要对其再次除以 DPI，也不要关闭高 DPI 支持或全局缩小字体绕开问题。

## 5. 建议修复设计

### 第一阶段：新建任务窗口恢复可用

1. **顶层保留标题栏、底部操作区，中间提供可滚动正文。** 使用 QFluentWidgets `ScrollArea`／`SmoothScrollArea`，`widgetResizable=True`。正文容纳信息卡、选择器、下载选项、裁切、目录以及错误／认证提示，取消与下载按钮留在视口外。错误态和加载态同样遵守窗口边界。
2. **去掉遗留空容器。** 顶层布局直接创建在窗口上，或使用真实参与布局的正文容器，避免先建布局再挪走。内容布局顶边保留标题栏高度；在内容构造完成／显示时确保标题栏处于可交互层级。
3. **解除外窗宽度锁。** 把模式尺寸改为初始偏好；去掉动画完成后恢复 760/880/980 下限及“+60”上限的规则。窗口宽高与位置统一夹进当前屏幕可用区。
4. **窄屏重排。** 下载选项改成可换行布局或两列；裁切的开始／结束／模式拆行；视频信息卡窄屏时允许缩略图上下排列；长标题、下载路径和英文文本不能撑宽顶层窗口。不能仅禁止横向滚动却让内容继续被裁掉。
5. **简易／专业页面按当前页计算尺寸需求。** 通过局部组件实现当前页的 size hint／size policy 切换，避免隐藏页抬高当前页下限；不做全局 Qt 或 QFluentWidgets monkey patch。这是优化，不能代替外层滚动。
6. **裁切主要展开正文，不强制扩张外窗。** 展开后滚动到新控件；若保留外窗动画，终点必须服从屏幕可用区，且用户已调整或最大化时不抢改位置／尺寸。清理旧动画回调，防止动画结束又恢复旧约束。

目录输入框保留正文中并通过滚动可达；操作按钮持续可见。若产品后续要求目录始终可见，可以放到固定底栏，但要增加窄屏重排和极短屏高度预算，不能让固定底栏反过来挤掉正文。

### 第二阶段：滚动与多屏行为收口

- 简易模式尽量让正文统一滚动，避免预设列表与外层双重滚动。专业表格、播放列表／频道列表保留必要的独立滚动和列表虚拟化；给列表合理视口高度，外层不能按全部行数展开，不能破坏懒加载触发。
- 初次打开以发起窗口所在屏幕为准；用户拖动后以当前窗口屏幕为准。当前 `_get_target_geometry()` 会优先找主窗口，后续重解析可能又以主窗口定位，应区分首次定位与后续内容变化。
- 处理 `screenChanged`、`availableGeometryChanged` 以及屏幕移除／缩放变化，必要时延后合并重算。切换订阅时断开旧屏幕信号，关闭窗口时清理；普通拖动不要不断强行居中。
- 保留用户位置、大小和最大化状态；恢复普通窗口时也要检查是否还在有效屏幕上。使用目标屏幕的完整矩形，包括负坐标及非零原点，不能假设全局原点是 `(0,0)`。

Qt 对滚动容器的说明也强调内容 size hint、布局约束与 `widgetResizable` 的配合，必须实测动态增删内容后的滚动范围。[QScrollArea](https://doc.qt.io/qt-6/qscrollarea.html#size-hints-and-layouts)

### 第三阶段：专业模式下拉、滚动与展开动效统一（新增，纳入本次交付）

1. **建立逐项对照。** 在普通／VR 专业模式中依次操作视频卡片、音频卡片、内层列表滚动条、外层滚动条以及下载模式／输出格式菜单。用同一窗口大小、缩放比例和等量数据对比；记录触发控件、鼠标落点、行数、展开状态和滚动范围，准确对应用户反馈的两处差异。
2. **统一流表格和滚动条。** 普通模式优先迁移到项目已有的 Fluent `TableWidget`，与 VR 采用一致的主题、滚动条宽度及悬停反馈、逐像素滚动和平滑滚动参数。核对所用组件已经安装的滚动委托，避免重复叠加动画；仅改滚动条样式表不足以解决运动响应差异。
3. **明确滚动归属。** 两张流卡片采用同一套视口高度规则，以可用空间和行数计算，取消普通模式“最多两行”的隐式体验限制。有限高度的列表内部滚动，正文负责卡片之间及其他选项的可达性；内部到达边界后，后续滚动交给外层。一次输入只由一层消费，不能两层同时移动、完全吞掉滚轮或产生多段迟滞。
4. **共享展开／收起动效。** 在 `FormatExpandCard` 统一实现正文高度过渡及箭头旋转，普通／VR、音频／视频共用。以已安装 Fluent 展开卡片的 200 ms 为初始对照，统一时长与缓动曲线，最终通过实际交互确定；这不是已验证的性能参数。展开高度按当前内容计算，动画只改变卡片正文，不推动顶层窗口越界。
5. **支持动画中断。** 连续点击、反向收起、切换简易／专业模式或解析结果更新时，从当前显示高度继续或取消动画；不跳回起点、不积累旧回调。收起结束后正文及其中控件不得继续接受焦点；展开和尺寸变化保持当前选择及合理滚动位置，初始化默认展开无需播放入场动画。
6. **菜单保持同一交互规范。** 检查下载模式、容器、音频格式等 `ComboBox` 的展开／收起、方向、菜单最大高度、菜单内滚动、Esc 和焦点返回。空间不足时允许向上弹出，但运动节奏和样式应一致；不把卡片手风琴强行替换成下拉菜单。当前 Fluent 菜单若无异常，保留原有实现。
7. **保护选择语义。** 替换表格或调整布局时，保留视频单选、音频多选、格式 ID 映射、选中摘要和下载参数。卡片展开、滚动或动画结束不得触发重复选择变更／下载事件，也不得清空用户已选流。

此阶段与前两阶段共同设计：新增正文滚动会改变事件落点和可用高度，应在最终布局中验证动画，不能在旧布局中单独调顺滑后就认定完成。共享 `FormatExpandCard` 与 `VideoFormatSelectorWidget` 的播放列表格式选择弹窗也要同步回归。

## 6. 验收与实施边界

建议最低完整验收的逻辑可用区先定为 640×480；这是设计目标，尚未验证能满足所有模式。更小区域需要单独定义退化行为，不能作无限制支持承诺。

- **几何回归：** 640×480、800×560、1280×680、720×1240、1920×1040；正／负坐标副屏、顶部／侧边任务栏。布局及动画稳定后窗口在有效可用区内，下载／取消按钮完整可见且可点击，不能只断言目标矩形。
- **内容回归：** 普通、VR、字幕、封面、播放列表、频道；简易／专业切换；长标题、长路径、中文／英文、亮／暗主题；裁切反复展开；Cookie 警告、错误详情、重试状态。底部目录能通过滚动和键盘到达。
- **交互回归：** 滚轮／触控板／滚动条／Tab 焦点；列表内部和外部滚动衔接；列表懒加载；标题栏空白区命中；关闭／最小化／最大化不被覆盖；用户拖动期间与重解析动画不互相争抢几何。
- **专业模式一致性（新增）：** 普通／VR、主配置窗／播放列表格式选择弹窗；视频与音频各准备 0、1、2、20、100 行，分别覆盖仅一张卡片溢出和两张同时溢出。相同操作下滚动条样式、悬停、滚动响应和展开节奏一致；测试滚轮、触控板连续／反向输入、拖动滚动条、快速反复展开、窗口缩放和模式切换。没有突然跳高、箭头与正文状态不同步、空白残留、焦点留在隐藏正文、丢选中或双层同步滚动。空列表反馈明确，所有非空列表首尾行均可达。
- **动效证据（新增）：** 自动化检查展开／收起最终高度、动画中断状态、滚动边界和选择不变性；Windows 实机对同一操作录制前后画面，并记录测试机刷新率、缩放、数据量及 UI 响应／动画帧间隔。是否顺滑以运行观察和测量为依据，不能用“换成 Fluent 控件”或离屏截图代替；本研究尚无这部分验收结果。
- **Windows 真机：** 1366×768 @100%/125%，1920×1080 @125%/150%/200%，2560×1440 @150%/200%，3840×2160 @200%/250%，1080×1920 竖屏 @125%/150%；记录每次实际 `availableGeometry`、DPR、字体和任务栏位置，不由分辨率推测。包含混合 DPI 跨屏、旋转、拔屏和最大化恢复。
- **发布验收：** 源码 offscreen 通过后，还需正式 Windows 构建在上述关键真实场景中验证；当前没有安装包修复或发布结论。

实现限制：只改显示布局、窗口几何与交互；保留任务构建、用户选项、解析缓存、后台调度及下载发射行为。无需引入新依赖或更改版本。

建议拆分提交为“标题栏／正文与底栏结构”“窄屏与屏幕几何策略”“专业流表格、滚动和展开动效统一”“邻近窗口适配”，每步附对应验证证据。回滚仅回退这些 UI 提交，不涉及数据迁移或配置清空；只增加滚动条或只提升标题栏均不能独立宣告本次 UI 问题全部修复。专业模式动效不一致是用户补充的本次交付范围，不能在仅解决窗口越界后遗漏。
